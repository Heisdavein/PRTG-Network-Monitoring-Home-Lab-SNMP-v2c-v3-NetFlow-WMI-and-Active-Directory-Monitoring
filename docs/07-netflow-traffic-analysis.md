# 7. NetFlow Traffic Analysis

## Overview

After SNMP, I realised there was still a question PRTG could not answer. It could tell me whether a device was online, how busy its CPU was and how much bandwidth crossed an interface, but not **who was using that bandwidth**. If my WAN interface hit 95% utilisation, SNMP would show it, but not whether the cause was a Windows update, a backup, someone streaming video, or malicious activity.

**NetFlow** solves this. It shows the *conversations* on the network: which devices talk, which applications they use, how much bandwidth each conversation takes and how patterns change over time. That turns troubleshooting from guesswork into evidence-based investigation.

---

## Understanding NetFlow

NetFlow was developed by Cisco. Instead of recording every packet like Wireshark, it summarises traffic into **flows**, which is far more efficient for continuous monitoring.

| Term | Meaning |
| ---- | ------- |
| **Flow** | A conversation between two devices. Packets belong to the same flow when they share source IP, destination IP, protocol, source port and destination port. A laptop copying files from my Synology NAS over SMB is one flow |
| **Flow export** | Network devices periodically package flow summaries and send them to a monitoring server. The exporter can be a router, firewall or Layer 3 switch. In my lab it is the **WatchGuard firewall** |
| **Collector** | The server that receives the exported flows. In my lab it is the **PRTG server** |
| **Top Talkers** | Which devices use the most bandwidth |
| **Top Protocols** | Traffic broken down by protocol (HTTPS, SMB, DNS, FTP, SSH, VPN and so on) |

### Why NetFlow version 9?

Compared with version 5, **version 9** adds IPv6 support, extensible templates, support for more traffic information and better compatibility with modern devices. Most current enterprise equipment supports v9, though some older hardware may still need v5.

---

## Step 1: Configure NetFlow on the WatchGuard Firewall

I went to **System → NetFlow**, enabled NetFlow and selected **Version 9**, then set the collector.

| Setting | Value |
| ------- | ----- |
| NetFlow version | 9 |
| Collector address | IP address of my PRTG server |
| Collector port | UDP 9996 |
| Active flow timeout | 1 minute |

- The **collector address** tells the firewall where to send flows.
- The **collector port** must match the port PRTG will listen on.

I also enabled export for:
- traffic generated by the firewall itself, and
- traffic destined for the firewall.

These flows are management traffic, not user traffic, but they can give useful security information if unusual activity appears.

Finally I chose the interface that exports flows: the **external WAN interface**, because I wanted visibility into internet traffic entering and leaving the network. I enabled both **Ingress** (incoming) and **Egress** (outgoing) before saving.

Enabling NetFlow does not noticeably affect normal firewall operation. The firewall keeps forwarding packets exactly as before and simply exports metadata about them in the background.

## Step 2: Add the NetFlow Sensor in PRTG

Inside **DMT-FW-01** I selected **Add Sensor**, searched for NetFlow and chose **NetFlow v9** (to match the firewall).

| Setting | Value |
| ------- | ----- |
| UDP listening port | 9996 |
| Sender IP | WatchGuard Firewall |
| Receiving interface | PRTG Server LAN Interface |
| Flow timeout | 1 minute |
| Filtering | None (I collected every flow first to understand my overall traffic profile) |

After I clicked **Create**, the sensor showed a waiting state until the first flows arrived.

> [!IMPORTANT]
> The UDP port and sender IP in PRTG must match the firewall configuration. If either is wrong, PRTG simply receives no flow data.

## Step 3: Verify That NetFlow Is Working

After about a minute the sensor started receiving data. It was immediately clear how much more information NetFlow gives than SNMP alone.

| View | What it showed me |
| ---- | ----------------- |
| **Top Protocols** | Bandwidth by protocol. Most of my lab traffic was HTTPS, HTTP and DNS, which made sense because my lab activity was mostly web browsing and software updates |
| **Top Talkers** | Devices ranked by bandwidth use, so I can spot the biggest consumers without asking every user |
| **Top Connections** | Individual conversations: source IP, destination IP, protocol and bandwidth |
| **Live Data** | A continuously updating graph broken down by protocol. Watching protocols rise and fall across the day gave me a baseline of normal behaviour, which makes unusual traffic obvious |

| Test | Expected result | Actual result | Status |
| ---- | --------------- | ------------- | ------ |
| Sensor leaves waiting state | Starts receiving flows | Began receiving data after about one minute | ✅ |
| Top Protocols view | Protocol breakdown shown | Mostly HTTPS, HTTP and DNS | ✅ |
| Top Talkers / Top Connections | Devices and conversations listed | Listed | ✅ |

## A Practical Troubleshooting Scenario

Imagine a user phones and says, *"The internet is really slow today."*

- **Without NetFlow** I would check firewall CPU, interface utilisation, ISP connectivity and switch performance, and might eventually find the cause.
- **With NetFlow** I can often answer in under a minute. If one workstation is uploading a 200 GB backup to cloud storage, it sits at the top of Top Talkers. If most WAN bandwidth is HTTPS, I can drill into the specific conversations responsible.

## NetFlow Best Practices

| Practice | Why |
| -------- | --- |
| **Choose an appropriate export interval** | I used a one-minute active flow timeout for near real-time visibility without overwhelming the collector. Exporting every thirty seconds gives more detail but doubles the volume of flow records |
| **Monitor the correct interfaces** | For internet analysis, export from the WAN interface. To analyse traffic between internal departments, monitor the uplinks on a core Layer 3 switch. The observation point matters as much as enabling NetFlow |
| **Protect flow data** | Traditional NetFlow exports are **not encrypted**. They contain no packet payloads, but still reveal communication patterns, so keep them on trusted internal networks and never send them across the public internet without extra protection |
| **Review trends regularly** | Looking at Top Talkers and protocol mixes each week builds a baseline, so unusual traffic is easy to spot |

## What I Took Away

Bandwidth alone tells only part of the story. **SNMP and NetFlow complement each other:** SNMP tells me how busy a device or interface is, and NetFlow explains why it is busy. Together they let me detect performance issues and investigate bandwidth use with evidence instead of opinion.
